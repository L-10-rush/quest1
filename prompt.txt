How this was actually built
----------------------------
I used Claude Code (Anthropic's CLI agent, running on the Sonnet model)
for the whole build. That's different from chatting with Claude.ai or
Gemini in a browser tab. Claude Code can read and write files in my repo,
run shell commands, and actually run the test suite and the Docker build.
So a lot of what's below happened as "here's the goal, go build it and
show me it passes," not "write me a snippet I'll paste in myself."

The assignment cares about whether I can actually direct and supervise an
AI coding session, not just whether I typed some prompts. So I've logged
the real sequence below, in order, including the spots where I course-
corrected or interrupted mid-task, because that's what actually happened.
The last section covers how to get a similar result using only the free
web versions of Claude or Gemini, since those don't have file or shell
access and need a different workflow.

I did the initial research and wrote the first draft of Approch.md myself,
before bringing in Claude Code. The prompts below start from there.

----------------------------------------------------------------------

[1] PURPOSE: kickoff, turn the research doc into a real project
PROMPT:
  "I have a problem statement and I've done some research and put it into
  Approch.md. They also want three files: approach.md (architecture,
  process diagram, sprint breakdown), prompt.txt (all prompts used,
  ordered, with model/purpose/summary, they're going to evaluate me on
  this), and README.md (full setup/startup guide with tech stack).
  Focus on Dockerizing the project, and make it well structured with
  solid, strong fundamentals. Clean code, properly commented."
RESULT: Claude caught a real contradiction before writing anything. My
  research doc assumed the dialogue was spoken (audio pipeline, WhisperX),
  but the actual problem statement PDF says "on-screen dialogue," which
  reads like burned-in captions instead. It asked me to confirm which one
  was actually true for the assignment video before building around the
  wrong assumption. Good catch. I hadn't reread the PDF closely enough.

[2] PURPOSE: resolve the audio-vs-OCR question, scope the output format
PROMPT:
  "In the given URL there's no caption or hardsubs, only audio dialogue
  and conversation, so build audio-based for now. Add OCR plus audio
  cross-confirmation as a documented future scope. Also keep a JSON file
  per video URL, a separate folder for the frame images, and put word
  counts/frequencies and other metrics in the JSON."
RESULT: This is the actual architecture decision that ended up in
  approach.md: audio-first pipeline, OCR explicitly deferred. It also
  shaped the output schema (per-video JSON, a frames/ folder, a
  transcript_metrics block) from day one instead of being bolted on later.

[3] PURPOSE: decide how much code Claude should write vs. scaffold
PROMPT (picked from a clarifying multiple-choice Claude asked):
  "Docker plus skeleton. Real Dockerfile/compose and a full module
  skeleton with interfaces and docstrings, but leave the core algorithm
  bodies for me to fill in."
RESULT: Why the early scaffold had detailed TODO docstrings instead of
  finished implementations. Architecture first, logic sprint by sprint.

[4] PURPOSE: Dockerize for real, switch to uv
PROMPT:
  "I've dockerized this current project and I use uv to manage package
  installation and running the project. Give me the README.md with all

[5] PURPOSE: Sprint 1, ingestion, for real this time
PROMPT:
  "Help me implement Sprint 1. Write the code for the ingestion layer:
  getting the video and its metadata. I also want the video to get a

  fastest searches. Plus its test code."
RESULT: A SQLite-backed VideoRegistry (auto-incrementing sequence IDs for
  filenames, indexed URL lookup so a repeat request skips re-downloading),
  wired to the real yt-dlp downloader. Learned that SQLite auto-increment
  is a much better fit here than a hand-rolled counter file. No race
  conditions to worry about.

[6] PURPOSE: make sure Sprint 1 actually holds up
PROMPT:

RESULT: Full coverage for the registry (cache hit/miss, self-healing when

  downloader (mocked at the yt-dlp/OpenCV boundary so tests run in
  milliseconds and need no network).

[7] PURPOSE: Sprint 2, matching and frame extraction
PROMPT:

  expect: my own test caught a real bug in the matching logic. A
  truncated candidate window was scoring higher than the correct
  full-width one, purely because of how token_sort_ratio handles string
  length, not because it was actually a better match. Needed a
  margin-based tie-break to fix it. Documented in approach.md because
  it's exactly the kind of thing I should be able to explain live.

[8] PURPOSE: Sprint 3, config, robustness, integration tests
PROMPT:
  "Help me complete Sprint 3, give me the test code, and update the docs."
RESULT: The pipeline got tested end-to-end for the first time, not just
  stage by stage. Fake stages standing in for the real ones proved an
  uncertain match still produces a complete result instead of failing
  silently, and that --language really flows through without touching
  pipeline code.

[9] PURPOSE: Sprint 4, the last two scaffolds, prove it actually works
PROMPT:
  "Go ahead with Sprint 4 and the remaining scaffolds. Update the unit
  tests for Sprint 4. Also help me test the complete project together."
RESULT: The most useful part of the whole build. Getting WhisperX to

  wouldn't load at all on my kernel until its exec-stack flag got
  patched. None of that shows up in a quick demo. It only shows up when
  you run the thing for real. Once it was fixed, I generated a synthetic
  speech clip and ran the full pipeline: correct transcript, correct
  frame, 98% match score.

[11] PURPOSE: fix a real bug found by actually running it against a live URL
PROMPT (pasted the actual error output from my own terminal):
  "[pasted a yt-dlp 'Requested format is not available' error from
  running the CLI against a real YouTube URL] Help me fix this error,
  also fix the Dockerfile if needed."
RESULT: The default format selector required a single progressive

  against the real video, not just rereading the code.

Getting an equivalent result on Claude.ai (free) or Gemini (free)
--------------------------------------------------------------------
Claude Code can read my files, run my tests, and run real commands. The
free web chat tools can't do any of that. They only give you text back.
So the prompts above still work as a sequence, but the workflow around
them changes:

  1. Ask for one stage at a time, and ask for the full file content, not
     a diff or a snippet. Free-tier chat has no memory of your actual
     files, so it can only work from what you paste back to it.
  2. After it gives you code, paste it into your own files and run the
     tests yourself: pytest, docker build, whatever applies. The model
     can't do this part for you.
  3. When something breaks, paste the actual error message back instead
     of describing it from memory. Prompt [11] above is a good example
     of this working well ("here is the real traceback, fix it") versus
     a vague "it doesn't work."
  4. Keep each prompt scoped to one stage or module, the same way the
     sprint breakdown above does it. A single "build the whole thing"
     prompt on a free plan will blow past the context window and you'll
     get a shallow, generic answer instead of something you can ship.
  5. For the dependency-pinning issues in [9] specifically: a free-tier
     model can reason about why torch, torchaudio, and torchvision need
     to match, but it can't verify the fix by actually installing
     anything. Expect to go back and forth pasting error messages a few
     times. That's normal, not a sign you're doing it wrong.

Everything else, the architecture decisions, the SOLID structure, the
uncertainty-handling design, the bug fixes, came from the same kind of
prompts either way. The real difference is whether the model gets to
verify its own answer, or you're the one running it and reporting back.
